## 07 · 协作规范

### 1. Git 分支模型
- `main`：始终可上线，只能通过 PR 合入。**部署门禁**（免费版私有仓库方案）：部署仅由 PR 合并触发，直接 push `main` 不会部署、且会被 CI 的「Main 直推拦截」job 标红。
- 功能分支命名：`feat/<模块>-<简述>`，例：`feat/profile-save-api`、`feat/detail-unlock-ui`
- 修 bug：`fix/<简述>`，例：`fix/pref-row-alignment`；文档/规范：`docs/<简述>`

**完整流程**：建分支 → push（自动触发对应区域的 CI workflow）→ 向 `main` 提 PR（AI 评审机器人自动评审）→ 必需检查全绿 → **用 merge commit 方式合并**（`gh pr merge --merge`；禁 rebase/squash，否则被「Main 直推拦截」误拦）→ 自动部署生产（`deploy.yml`）。

**CI 按区域拆分（原生路径过滤，不相关区域零启动成本）**：
- `ci-backend.yml`（backend/**、deploy.sh、workflow 变更）：Lint & Tests（SQLite 并行）+ Tests (PostgreSQL)
- `ci-admin.yml`（admin/**、workflow 变更）：Lint, Test & Build + 每周一 e2e
- `ci-miniprogram.yml`（miniprogram/**、tests/**）：语法检查 + 旅程测试
- `ci-compose.yml`（Dockerfile/compose/deploy 脚本/锁文件）：compose 冒烟——普通业务代码 PR 不再构建 docker 镜像
- `ci-main.yml`（main 每次 push 必跑）：Main 直推拦截

**分钟数说明**：区域 CI **只在 PR 事件跑**，合并到 main 后不重复跑（PR 已把关；多 PR 并行时合并前点一下 *Update branch* 重跑检查兜底语义冲突）。纯文档/服务器运维脚本类合并不触发部署。LLM 评审管线已于 2026-09 退役（单人 AI 开发场景下性价比最低的项）；e2e 降为每月 1 号。剩余开销集中在测试本身，上自建 runner 后归零。

**合并前必须通过的必需检查**：Backend — Lint & Tests / Backend — Tests (PostgreSQL) / Admin — Lint, Test & Build / Miniprogram Lint / Miniprogram Journey Test / Compose Smoke。路径不匹配的区域不会产生检查项（视为通过）。

**进一步提速（可选，自建 runner）**：在服务器安装 self-hosted runner 后，CI 可切到本机跑——uv/npm 缓存常驻（省每次 ~50s 冷启动）、完全零分钟数消耗、部署也不用 SSH 中转。步骤：
```bash
# 服务器上 (root), 版本号以 GitHub Settings → Actions → Runners → New self-hosted runner 页面为准
mkdir -p /opt/gh-runner && cd /opt/gh-runner
curl -o runner.tar.gz -L https://github.com/actions/runner/releases/download/v<X.Y.Z>/actions-runner-linux-x64-<X.Y.Z>.tar.gz
tar xzf runner.tar.gz && ./config.sh --url https://github.com/guanlili/qianchenhunlian --token <页面生成的 token> --name qy-prod
./svc.sh install && ./svc.sh start
```
然后把各 ci-*.yml 的 `runs-on: ubuntu-latest` 改为 `runs-on: [self-hosted]` 即可（建议逐个 workflow 切换观察）。注意：CI 构建会与生产容器竞争 CPU，观察部署期间响应再决定全量切换。

**紧急情况**：
- 线上故障：优先用服务器 `./deploy.sh` 的 `:prev` 镜像回滚（分钟级），再走 `fix/*` PR 修根因
- CI 全挂需要紧急发版：workflow_dispatch 手动触发部署是唯一兜底通道（慎用）

**升级 GitHub Pro 后**（可选，强化为真正的分支保护——UI 层面禁止直推与红 CI 合并）：
```bash
gh api -X PUT repos/guanlili/qianchenhunlian/branches/main/protection --input - <<'EOF'
{
  "required_status_checks": {"strict": false, "contexts": [
    "Backend — Lint & Tests", "Backend — Tests (PostgreSQL)",
    "Admin — Lint, Test & Build", "Miniprogram Lint",
    "Miniprogram Journey Test", "Compose Smoke"
  ]},
  "enforce_admins": true,
  "required_pull_request_reviews": {"required_approving_review_count": 0},
  "restrictions": null,
  "allow_force_pushes": false,
  "allow_deletions": false
}
EOF
```

### 2. Commit 规范
用常见的 Conventional Commits 风格，小步提交：
- `feat(cf-profile): 新增 saveProfile 接口`
- `feat(mp-detail): 对接 match.getProfile`
- `fix(mp-my-profile): 择偶要求 label 对齐`
- `docs: 更新 04-云函数接口 错误码说明`
- `chore: 删除示例 example 页`
- `refactor(mp): 抽取 services/profile.js`

规则：
- 一个 commit 只做一件事，避免"改了资料页顺便改了登录"的混合提交
- 提交信息中英文均可，保持团队内一致
- 禁用 `--no-verify` 跳过钩子

### 3. PR 规范
- 标题与 commit 规范一致
- 描述必须包含：改动范围 / 测试方式 / 需要哪边联调
- 模板：
  ```
  ### 改动
  - 新增 XXX
  - 修正 YYY

  ### 测试
  - [ ] 已在开发者工具本地跑通
  - [ ] 联调: 需要 @对方 在 devEnv-xxx 一起看

  ### 关联
  docs/04-云函数接口.md#X.Y
  ```
- 另一人 approve 后合并；紧急情况自评并补上 follow-up。

### 4. 代码风格
小程序端：
- 2 空格缩进，单引号
- 页面 js 中业务相关数据放 `data`，纯视图辅助用 computed/临时变量
- 所有调云函数通过 `services/`，页面里不 `wx.cloud.callFunction` 直接裸调
- 常量（学历/收入/婚况等枚举）放 `constants/`，前后端必须保持一致，后续考虑用 ts 或 json 共享
- wxss 颜色集中到 `app.wxss` 的 CSS 变量（后续迭代）

云函数端：
- 每个云函数 `index.js` 以 `event.action` 路由，子处理器放 `./handlers/<name>.js`
- 入参必须白名单 + 类型校验
- 错误统一抛 `throw { code, msg }`，在 main 里 catch 成标准响应
- 任何 db 写入后返回的数据要是"真实最新"版本，避免前端再拉一次

### 5. 字段与枚举一致性
- 学历、收入、婚况、婚房等枚举：后端以 `profile.saveProfile` 的白名单为准；前端常量必须和后端同步
- 日期字段：后端一律 `db.serverDate()`，前端格式化时用 `utils/date.js`（待建）

### 6. 联调约定
- 后端接口 ready 前先提供 mock：在 `index.js` 里对 action 硬编码返回示例数据，前端可以先接起来
- 前端在页面显示"接口 mock 中"标记（dev 环境开关）
- 联调时两人一屏幕，一次对一个 action

### 7. 文档更新
- 任何改接口的 PR 必须同时改 `docs/04-云函数接口.md`
- 任何改数据库 schema 的 PR 必须同时改 `docs/03-数据库设计.md`
- `docs/08-待确认事项.md` 有新增 / 关闭时，带上日期和决策人

### 8. 版本与发布
- 开发环境：每次 PR 合入后由 PR 提交者部署到公用 devEnv
- 预发布：MVP 联调完成后申请一个 testEnv，用来体验版
- 生产：上线前最后一次 PR 带 tag `v1.0.0`

### 9. 敏感信息
- 不要把 env id、管理员 openid、模板 id 提交到仓库
- 这类配置放 `miniprogram/envList.js`（已 gitignore 或另行约定）或云函数的 `config.json`（后端侧）
- 联系方式字段在云函数内处理，永远不要在前端日志或错误信息里打印

### 10. 代码检查清单（Code Review 前自检）
- [ ] 新增字段是否同步到 03 文档？
- [ ] 新增 action 是否在 04 文档？
- [ ] 有没有打印 openid 到生产日志？
- [ ] 新增云函数是否做了入参校验？
- [ ] 前端 loading / 错误态 / 空态是否处理？
- [x] `pages/example/`、`quickstartFunctions` 有没有被新代码引用？（已全部清掉，无残留）
