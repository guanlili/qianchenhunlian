# 全局身份与权限矩阵

> 本文是整个平台「谁能在哪里做什么」的单一总览。此前相关规则散落在
> `permissions.py` / `membership.py` / docs/10 / docs/11 / docs/13，本文统一收口。
> **代码仍是事实来源**，本文与后台「使用指引 → 角色权限说明」页与之保持同步。

## 0. 核心设计：两个维度，两套系统，不要合并

平台的「角色」实际是两个**正交维度**，刻意用两套独立机制实现：

| 维度 | 回答的问题 | 机制 | 代码位置 | 变更方式 |
| --- | --- | --- | --- | --- |
| **后台操作权限**（RBAC） | 管理者在后台*能做什么* | 静态权限矩阵，fail-closed | `app/api/permissions.py` | 改代码 + 评审 |
| **小程序权益额度**（订阅制） | 用户在小程序*能用多少* | 三桶额度引擎 + 可配置套餐 | `app/core/membership.py` | 后台直接调参数 |

**为什么不建动态角色系统（Role/Permission 五表）**：组织结构固定（总部+门店）、
后台只有两种角色、变更频率极低。静态矩阵的好处正是安全特性本身——
fail-closed（未知角色一律拒绝）、权限变更必须走代码评审、
不存在「后台误点一下就跨店越权」的配置风险。升级触发条件见 §5。

## 1. 五种身份一览

| 身份 | 判定 | 场景 |
| --- | --- | --- |
| 系统管理员 | `User.is_superuser = true` | 后台 |
| 门店管理员 | `Staff.role = 'store_admin'` 且 `store_id` 非空 | 后台 |
| 付费会员 | `membership_expires_at > now`（`is_member()`） | 小程序 |
| 注册用户（非会员） | 已登录小程序、会员过期或从未开通 | 小程序 |
| 游客 | 未登录 | 小程序 |

注意：`store_id` 缺失的门店管理员视为**配置残缺，按普通用户处理**（fail-closed）。
历史角色 `matchmaker` 已迁移为 `store_admin`；`hq_staff` 已废弃，一律无权限。

## 2. 后台权限矩阵（16 权限点 × 2 角色）

「仅本店」= 数据范围限制，由 admin 路由的 store scope helper
（`_store_owner_id` / `_check_member_scope`）负责，与功能权限分开判定。

| 权限点 | 系统管理员 | 门店管理员 | 说明 |
| --- | :-: | :-: | --- |
| 资料审核（线上） | ✓ | ✗ | 用户提交的资料审核 |
| 编辑/代录会员资料 | ✓ | ✓ 仅本店 | 基本资料、择偶要求等 |
| 实名认证 | ✓ | ✓ 仅本店 | 通过/驳回实名认证 |
| 查看会员联系方式 | ✓ | ✓ 仅本店 | 记审计日志 |
| 工单内联系方式 | ✓ | ✓ 仅本单归属店 | 撮合工单详情内 |
| 撮合工单处理 | ✓ | ✓ 仅本店工单 | 处理联系申请 |
| 撮合工单改派 | ✓ | ✗ | 修改工单归属门店 |
| 赠送解锁次数 | ✓ | ✓ 仅本店会员 | 联系解锁额度 |
| 会员开通/续费/回收 | ✓ | ✓ 仅本店会员 | docs/13 |
| 封禁/解封会员 | ✓ | ✓ 仅本店会员 | |
| 门店管理 | ✓ | ✗ | CRUD / 指定主属门店 |
| 平台设置 | ✓ | ✗ | 资质 / 公告 / 协议文案 |
| 意见反馈处理 | ✓ | ✗ | |
| 员工账号管理 | ✓ | ✗ | |
| 管理员账号管理 | ✓ | ✗ | |
| 操作审计日志查看 | ✓ | ✗ | |

其余任何账号（小程序用户 / 未知角色）在后台 = 无权限，所有后台接口 403。

## 3. 小程序身份与额度

额度消耗点：**发起联系申请**（`routes/contacts.py` 调 `membership.consume`），
三桶按序扣减：`member_daily → free_daily → balance`，全空返回 None（接口 402）。

| 身份 | 能做什么 | 联系申请额度 |
| --- | --- | --- |
| 游客 | 门店列表、平台资质、协议文案等公开内容（IP 限流） | 无，需注册 |
| 注册用户（非会员） | 浏览 / 搜索资料、完善自己资料 | 每日 5 次免费，超出扣余额 |
| 付费会员 | 同上 + 会员标识，到期自动降回非会员 | 每日 20 次，超出扣余额 |

套餐参数（日额度数字、套餐定价）存在 `site_settings`，后台可调，无需发版。

## 4. 新增后台功能时的登记流程

1. 在 `Perm` 枚举登记权限点（中文注释写清数据范围）；
2. 在 `ROLE_PERMS` 决定放行哪些角色（默认只给 superuser）;
3. 路由挂 `dependencies=[Depends(require_perm(Perm.X))]`；
4. 涉及会员个体的操作加 `_check_member_scope`（门店管理员仅本店）；
5. **同步更新本文 §2 表格和后台使用指引页的 `permMatrix`**。

## 5. 何时升级为动态角色系统（触发条件）

出现以下任一需求时再引入 Role/Permission 数据表：

- 出现**区域经理**类角色（一人管多店，单店 scope 撑不住）；
- 门店之间需要**差异化权限**（如某店不给看联系方式）；
- 引入**加盟 / 多租户**模式。

届时 `require_perm()` 工厂的设计让切换成本很低——调用点不用改，
只把矩阵来源从代码换成 DB 查询。在那之前保持静态。
